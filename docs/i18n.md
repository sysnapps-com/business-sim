# Internationalization (i18n)

This project is a client-side JavaScript game with no bundler or localization
dependency. Internationalization is implemented with ES modules in `src/i18n/`
and native browser `Intl` APIs. English (`en`) and Spanish (`es`) are currently
supported.

Localization changes display text and formatting only. Keep simulation values,
configuration keys, saved identifiers, and company/office/role IDs
language-independent.

## Architecture

- `src/i18n/en.js` and `src/i18n/es.js` are the translation catalogs. They use
  nested JavaScript objects and matching leaf keys.
- `src/i18n/index.js` owns the supported-catalog registry, active locale,
  translation lookup and interpolation, English fallback, label fallback,
  plural selection, locale detection/persistence, and formatting helpers.
- `src/i18n/dom.js` applies translation keys declared in static HTML and sets
  the document's `lang` attribute.
- `src/ui/language.js` populates the HUD language selector and changes the
  active locale.
- `src/main.js` initializes the locale before building UI, then refreshes
  active screens when the `locale-change` event is dispatched.
- `tools/check-i18n.js` checks catalog parity, interpolation placeholders,
  static HTML keys, and literal `t()`/`tp()` references in source.

The catalogs are deeply frozen at runtime. Changing locale updates existing UI;
it does not reload the page, reset the simulation, or alter game-state data.

## Translation key naming

Use descriptive, dot-separated keys grouped by the screen, component, or
message type:

```text
hud.build
intro.chooseCompany
build.notEnoughFunds
toast.loanReceived
event.titles.market_boom
content.offices.seo
```

Conventions:

1. Use lower camel case for ordinary key segments (`firstRoom`,
   `notEnoughFunds`); preserve existing identifiers as key values where a
   catalog maps an internal ID to display text (for example
   `content.offices.seo`).
2. Organize by UI area or purpose, not by source filename. Prefer
   `toast.loanReceived` to a generic key such as `message3`.
3. Keep stable internal IDs (company type, room type, event ID, equipment
   option) unchanged. Use them as catalog lookup keys when translating their
   display labels.
4. Use `{placeholder}` names for dynamic values, such as
   `toast.hired: '{name} hired successfully!'`. Keep the same placeholder names
   in every locale.
5. For plural messages, use a parent key with `.one` and `.other` leaves, for
   example `employee.agents.one` and `employee.agents.other`, and call `tp()`.
6. Avoid embedding HTML in ordinary strings. A catalog value intended for
   `data-i18n-html` must contain trusted, static markup only; never interpolate
   player-controlled or otherwise untrusted text into HTML.

## Adding or changing a translation

1. Add or edit the key in **every supported catalog** in `src/i18n/`.
2. Keep the same nested shape and interpolation placeholders in each locale.
3. For a new plural message, provide `.one` and `.other` in every catalog and
   use `tp(key, count, params)`.
4. Reference the key through `t()`/`tp()` in JavaScript, or through the
   appropriate `data-i18n` attribute in static HTML.
5. Run the catalog checker described in [Testing completeness](#testing-completeness).
6. Switch the app to each locale and inspect the rendered message in context,
   including long text, dynamic values, and narrow layouts where relevant.

Example catalog entries:

```js
// src/i18n/en.js
toast: {
  hired: '{name} hired successfully!',
  agents: {
    one: '{count} agent',
    other: '{count} agents',
  },
},
```

```js
// src/i18n/es.js
toast: {
  hired: '¡{name} ha sido contratado!',
  agents: {
    one: '{count} agente',
    other: '{count} agentes',
  },
},
```

## Translating a UI component

### Static HTML

Add a key to each translatable text or title and provide a readable English
initial value in the markup:

```html
<button data-i18n="hud.build" data-i18n-title="hud.buildTitle">
  Build
</button>
```

`applyDocumentTranslations()` handles:

- `data-i18n`: replaces the element's text using `textContent`.
- `data-i18n-title`: translates the element's `title` attribute.
- `data-i18n-html`: replaces `innerHTML` with trusted catalog content.

The HTML translations are applied during startup and again after locale
changes. Use `data-i18n-html` only when static, catalog-owned markup is
necessary (for example, fixed `<kbd>` or `<strong>` markup). Do not build HTML
translations by concatenating dynamic strings.

### Dynamic DOM or canvas UI

Import the service from the component and translate user-visible strings at the
point where they are rendered:

```js
import { formatCurrency, t } from '../i18n/index.js';

label.textContent = t('toast.hired', { name: agent.name });
amount.textContent = formatCurrency(companyRevenue);
```

Use `textContent` for plain text. If a component uses `innerHTML`, ensure dynamic
values are escaped or assembled as DOM nodes; `t()` interpolation is not an
HTML-escaping mechanism.

For config-backed labels, retain the original value/ID and translate only the
display label:

```js
import { translateLabel } from '../i18n/index.js';

const officeName = translateLabel(
  `content.offices.${office.typeKey}`,
  office.type.name,
);
```

For canvas text, call `t()` or `translateLabel()` where the drawing label is
generated. Refresh or redraw that canvas from the `locale-change` event, as
appropriate. Components with their own open/closed state should refresh only
the visible content and must not reset simulation state.

`setLocale()` dispatches a `locale-change` event only when the normalized locale
actually changes. The application bootstrap listens to it to refresh the DOM
and selected screens. If a new UI surface caches rendered strings, register a
refresh listener or include it in the existing application refresh path.

## Locale detection and switching

`initializeLocale()` is called near the beginning of `src/main.js`, before
static translations and UI initialization. Locale selection order is:

1. A valid saved preference from local storage.
2. The first supported language found in `navigator.languages`, in browser
   preference order. If that list is unavailable or empty, use
   `navigator.language`.
3. English (`en`) if no supported browser language is found.

Locale codes are trimmed and lowercased. The language portion is used, so
regional variants such as `es-MX` and `es_MX` resolve to `es`; unsupported
languages resolve to the next candidate or English.

The HUD selector is populated from `getSupportedLocales()`. When adding a
locale, also add its user-facing language name in `src/ui/language.js`.

## Locale persistence

The preference is stored under the independent local-storage key
`business_tycoon_locale_v1`; it does not share or overwrite game-state data.
`setLocale(locale)` persists the normalized supported locale by default.
`initializeLocale()` reads the stored value but does not write during startup.
An invalid or unavailable stored value is ignored and browser detection is
used instead.

Local-storage access is guarded. If reading or writing storage is blocked, the
locale still initializes from browser settings and can still be changed for the
current session; it simply will not persist across reloads. Calling
`setLocale(locale, { persist: false })` changes the in-memory locale without
writing storage. The optional `dispatch: false` suppresses the change event
(used during startup before UI exists).

## Missing-translation fallback

`t(key, params)` checks the active locale first, then English:

1. If the active locale contains a string for the key, use it.
2. Otherwise, use the English string if present.
3. If neither catalog contains a string, return a visible `⟦key⟧` diagnostic.
   An invalid or empty key returns `⟦invalid-translation-key⟧`.

Provided placeholders are interpolated as strings. A missing parameter remains
visible as `{parameter}` to help identify the omission; `null` or `undefined`
values supplied for a placeholder become an empty string.

`translateLabel(key, fallback)` looks in the active catalog, then English, and
finally returns the supplied original label. This is useful for data-driven
names so missing translations do not hide the underlying config value.

`tp(key, count, params)` selects a plural category with `Intl.PluralRules`, then
tries the corresponding `key.<category>` entry followed by `key.other` (with
English fallback at each step). It supplies a locale-formatted `{count}` value.
The current English and Spanish catalogs use `.one` and `.other`.

## Formatting utilities

Use the exported helpers from `src/i18n/index.js` for displayed values:

```js
import {
  formatCurrency,
  formatDate,
  formatNumber,
  formatRelativeTime,
  pluralCategory,
  tp,
} from '../i18n/index.js';

formatNumber(12345.6);                  // Locale-aware decimal/grouping
formatNumber(0.25, { style: 'percent' });
formatCurrency(12345);                  // USD, zero fractional digits by default
formatDate(new Date(), { dateStyle: 'medium' });
formatRelativeTime(-2, 'day');          // Locale-aware relative time
pluralCategory(2);                      // Intl plural category
tp('employee.agents', 2);               // Translation with plural selection
```

All formatting uses the active locale and native `Intl` behavior. `formatNumber`
accepts `Intl.NumberFormat` options. `formatCurrency` uses USD and defaults to
zero maximum fraction digits; supplied options can override those defaults.
`formatDate` accepts `Intl.DateTimeFormat` options, and `formatRelativeTime`
accepts the options supported by `Intl.RelativeTimeFormat`. Use the options
needed for the context rather than assembling separators or currency symbols
manually.

## Testing completeness

Run the standalone checker from the repository root:

```sh
node --experimental-default-type=module tools/check-i18n.js
```

It verifies:

- Every supported catalog has the same translation leaf keys.
- Matching keys use the same interpolation placeholders.
- `data-i18n`, `data-i18n-title`, and `data-i18n-html` references in
  `index.html` exist.
- Literal calls to `t('...')` and `tp('...')` under `src/` resolve; plural
  calls must have `.one` and `.other` entries.

The checker is static and cannot reliably discover generated keys such as
``t(`content.offices.${officeKey}`)`` or dynamically assembled translation
paths. Review those mappings manually. The checker also cannot determine
whether every visible phrase has been translated, whether translations are
linguistically correct, or whether long text fits visually. For a release,
manually switch between every supported locale and inspect onboarding, the
HUD, build/hire flows, open panels/popovers, charts, event modals, notifications,
and narrow-screen layouts. Exercise dynamic states and interpolation values as
well as the initial screen.

There is no project-wide automated browser or gameplay test suite. Run
JavaScript syntax checks and the manual UI checks when changes affect runtime
rendering.

## Adding a third language

For example, to add French (`fr`):

1. Create `src/i18n/fr.js` by translating the complete catalog structure. Keep
   every leaf key and placeholder aligned with the existing catalogs.
2. Import it in `src/i18n/index.js` and register it in `catalogs`:

   ```js
   import fr from './fr.js';

   const catalogs = deepFreeze({ en, es, fr });
   ```

   `getSupportedLocales()` and locale normalization derive their supported
   language list from this registry.
3. Add `fr: 'Français'` to `languageNames` in `src/ui/language.js`.
4. Run `node --experimental-default-type=module tools/check-i18n.js` and
   correct missing keys or placeholder differences.
5. Test `setLocale('fr')`, browser detection with a French preference,
   persistence/reload behavior, date/number/currency formatting, plural cases,
   and all key UI flows in the browser.
6. Update any locale-specific expectations in documentation or tests. Do not
   add language branches to simulation or business logic.
